# Booking UI Rework Implementation Plan

Date: 2026-07-16

Goal: implement the new public booking contact flow with the simplest possible user experience.

Core user path:

```text
Select employee -> select services -> select time -> contact info -> SMS code -> overview -> success
```

User-facing rules:

- Mobile verification is the only required identity verification.
- Email is optional.
- If email is provided, save it and use it for confirmation email.
- Email must never block booking.
- No email verification screen inside booking.
- No account creation screen before booking.
- Profile/account completion is optional after the appointment is booked.

---

## 1. Backend Calls To Use

Use generated booking SDK methods:

- `PublicAppointmentSessionController.getAppointmentSession`
- `PublicAppointmentSessionController.getAppointmentSessionRequirements`

- `PublicAppointmentSessionController.setPendingAppointmentSessionUser`
- `PublicAppointmentSessionController.submitAppointmentSession`

Use generated base SDK method:

- `Base.complete`

Do not use these old booking contact APIs in the new booking flow:

- `AuthController.signUp`
- `AuthController.providerCompleteProfile`
- `AuthController.verifyMobile`
- `AuthController.resendVerificationEmailOnly`
- `AuthController.resendVerificationMobileOnly`
- `VerificationTokenService` for booking routes

## 2. Route Shape

Keep these booking routes:

- `/booking/public/appointment/session/employee`
- `/booking/public/appointment/session/select-services`
- `/booking/public/appointment/session/select-time`
- `/booking/public/appointment/session/contact`

- `/booking/public/appointment/session/contact/sign-in`
- `/booking/public/appointment/session/overview`
- `/booking/public/appointment/success`

Remove from booking flow:

- `/booking/public/appointment/session/contact/sign-up`
- `/booking/public/appointment/session/contact/verify-email`
- `/booking/public/appointment/session/contact/collect-email`
- `/booking/public/appointment/session/contact/collect-mobile`

If deleted URLs need a graceful fallback, add tiny redirect routes to `/contact`; otherwise let them 404.

## 3. Implementation Checklist

### Route Implementation Blueprint

Use the `select-time` route as the current target shape for public booking routes.

Rules:

- Keep route behavior visible in the route file.
  - Exported `loader` owns loader logic directly.
  - Exported `action` owns action logic directly.
  - Do not add private `someRouteLoader` / `someRouteAction` wrappers unless there is real reuse.
- Keep flow decisions in the route.
  - Redirects, guards, backend calls, and final route links should be readable from the route.
  - Do not return simple route maps from loaders just so JSX can link to another booking step.
  - Use `const routes = getBookingRouteMap()` in the component when links are static booking routes.
- Use feature-local files for route-specific UI.
  - Put route-only components in `app/routes/booking/public/appointment/session/{step}/_components`.
  - Put route-only pure helpers in `app/routes/booking/public/appointment/session/{step}/_utils`.
  - Keep tiny leaf components in local files when they make the route easier to scan.
  - Avoid wrapper/orchestrator components that hide the route flow or nest route-specific components inside another route-specific component.
- Use shared booking components only for truly shared primitives.
  - Use `BookingLink`, `BookingActionButton`, and `BookingFooterNav` for simple footer navigation.
  - Keep `BookingBottomActionBar` out of renovated routes unless a route genuinely needs the old action config abstraction.
- Prefer direct JSX for route footer buttons.
  - The route should show exactly where `Tilbake`, `Fortsett`, and submit actions go.
  - Use normal links for step navigation when possible.
  - Use `reloadDocument` only when SPA navigation is proven to break user flow.
- For small save interactions, prefer `fetcher.Form`.
  - Use route `action` for backend persistence.
  - Use `fetcher.formData` for optimistic selected UI.
  - Add `preventScrollReset` when mutation should not jump the page.
- Keep backend-backed state as the source of truth.
  - Optimistic UI is only temporary display while a request is pending.
  - After backend response, loader/session data should remain authoritative.
- Keep tests aligned with the intended shape.
  - Tests may assert route structure when it protects against previous regressions.
  - Do not make tests force unnecessary abstractions.

Renovation order:

- [x] `select-time`: route-owned flow, local components/utils, shared footer controls, `fetcher.Form` for time selection.
- [x] `employee`: inline loader/action, remove loader navigation map, use shared footer controls, move profile card/service list UI into local `_components`.
- [x] `select-services`: inline loader/action, remove loader navigation map, use shared footer controls, move service card/group/image dialog UI into local `_components`.
- [x] `overview`: inline loader/action, remove loader navigation map, use shared footer controls, move formatting/helpers and overview sections into local `_components` / `_utils`.
- [x] `contact`: keep resolver behavior clear in route, move form/card-only UI to local components without hiding flow decisions.
- [x] `verify-mobile`: keep SMS state and action intents visible, move code-entry UI to local components if it improves scanability.

### Phase 2: Contact State Resolver

- [ ] Keep the `/contact` loader as the single owner of contact state.
  - Do not spread the decision across layout, shared components, or auth helper redirects.
  - It is OK to use tiny helper functions for parsing display data, but the route must show the flow order clearly.

- [ ] Contact loader decision order must be exactly:
  1. Backend says a mobile code is pending -> redirect to `/contact/verify-mobile`.
  2. Backend says the session already has a verified user -> render a resume card.
  3. Browser has auth tokens/current user -> render a continue-as bar.
  4. Otherwise -> render the contact form.

- [ ] Loader should fetch the minimum state needed for that order:
  - `requireBookingSession(request)` for the appointment session.
  - `getAppointmentSessionRequirements({ path: { sessionId } })` for backend booking state.
  - Current browser/auth user only after backend does not require SMS and does not already say `DONE`.
  - Do not call old email/mobile verification token helpers from the contact route.

- [ ] Loader should return one simple `contactState` discriminant:
  - `VERIFY_MOBILE_REDIRECT`
  - `RESUME`
  - `CONTINUE_AS`
  - `FORM`
  - `ERROR`

- [ ] Returned data shape should be explicit and boring:
  - `session`
  - `requirements`
  - `contactState`
  - `resumeUser` for `RESUME`
  - `authenticatedUser` for `CONTINUE_AS`
  - `requirementsError`

- [x] Map backend `nextStep` directly:
  - `CONTACT_FORM` -> contact form
  - `VERIFY_MOBILE` -> SMS code screen
  - `DONE` -> overview or resume card, depending route/user action

- [x] Do not handle email verification states in booking.

- [ ] Add pre-contact selection guard:
  - if no employee selected -> redirect `employee`
  - if no services selected -> redirect `select-services`
  - if no time selected -> redirect `select-time`

### Phase 3: Contact Form

- [x] Rebuild `/contact` as a simple contact form.

- [ ] `/contact` should render exactly one of these UI states:
  1. `RESUME`: card saying the contact info is already verified.
  2. `CONTINUE_AS`: compact bar/card for the logged-in browser user.
  3. `FORM`: name, mobile, optional email, and sign-in link.
  4. `ERROR`: form plus a clear non-blocking error notice when requirements could not be fetched.

- [ ] `RESUME` UI:
  - Copy: `Kontaktinformasjonen din er bekreftet`
  - Show name and masked mobile if backend returns them.
  - Primary: `Fortsett til booking`
  - Primary target: `/booking/public/appointment/session/overview`
  - Secondary: `Endre kontaktinformasjon`
  - Secondary action: `clearAppointmentSessionUser`, then reload `/contact`.

- [ ] `CONTINUE_AS` UI:
  - Copy: `Fortsett som {navn}`
  - Small secondary action: `Ikke deg?`
  - Primary action should attach the authenticated user with backend session attach/set-pending flow, then resolve requirements again or continue to the next correct step.
  - `Ikke deg?` should show the plain contact form for this booking session.
  - Do not force sign-in if the user wants to continue as guest.

- [x] Fields:
  - `givenName`, required
  - `familyName`, required
  - `mobileNumber`, required
  - `email`, optional

- [ ] Email helper copy:
  - `Valgfritt. Vi sender bekreftelsen på e-post også.`

- [ ] Primary button:
  - `Fortsett til SMS-bekreftelse`

- [ ] Secondary link:
  - `Har du allerede en konto? Logg inn`

- [ ] On submit:
  - call `identifyAppointmentSessionUser`
  - trim form values before sending.
  - send `email` only if the user filled it in.
  - if backend returns `VERIFY_MOBILE`, redirect to `/contact/verify-mobile`.
  - if backend returns `DONE`, redirect to `/overview`.
  - do not block booking on email.

- [x] Do not show Google/OAuth buttons on this screen.

- [x] Do not show `Opprett konto`.

## 4. Non-Negotiables

- [x] Booking must be possible with name + mobile only.
- [x] Email must be optional.
- [x] Email must never route to booking email verification.
- [x] SMS verification is the only required verification.
- [x] No account creation before appointment is booked.
- [x] Do not clear appointment session on transient failures.
- [ ] One primary action per screen.
- [x] If the backend says `DONE`, move the user forward.

---

## 5. Implementation Order

1. Session-only guard and step order.
2. Contact state resolver.
3. Contact form with identify.
4. Verify mobile with challenge/resend.
5. Overview guard and submit response.
6. Success page and optional profile completion.
7. Delete old booking contact routes.
8. Test cleanup and regression coverage.

Do not build extra states unless a real backend response requires them.
