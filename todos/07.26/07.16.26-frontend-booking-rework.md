# Pitell guest booking — frontend contact flow plan (rev 2)

Status: approved direction, companion to backend plan rev 3.4
Rev 2: step order changed to employee → services → time → Kontakt → overview; provider login
tucked behind the "Logg inn" link; challengeId carried as URL query param.
Scope: rebuild the public booking contact step on the new guest identity API; retire the
account-first contact flow; immediate hotfix for the old flow while the rework is built.
Root complaint addressed: user 1183 ("Aaron") — email verification felt required and blocking,
and returning to the contact page showed an unregistered state despite a valid backend session.

Principle: the frontend renders backend state, it never computes identity state. One resolver
(`/requirements`), one canonical route per state, idempotent loaders.

---

## 1. Decisions

| #   | Decision                 | Choice                                                                                                                                                                                                                                                                                               |
| --- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | Flow model               | Guest contact flow on the new identify/verify API. No account creation, no password, no email verification anywhere inside booking.                                                                                                                                                                  |
| F2  | State source             | `GET /requirements` is the single resolver. Frontend never derives nextStep locally. Both old frontend resolvers are deleted for booking.                                                                                                                                                            |
| F3  | Loader contract          | Every contact route loader: read session cookie → fetch session + requirements → derive one UI state → redirect to canonical route if mismatched. Refresh/back/forward are idempotent by construction.                                                                                               |
| F4  | Session cookie           | `appointment_session` is never cleared on transient fetch failure. Cleared only when the backend explicitly reports the session stale/invalid.                                                                                                                                                       |
| F5  | Challenge state          | `challengeId` travels as a URL query param on the verify-mobile route — no cookie, survives refresh within the 600s TTL, not a secret (the SMS code is). Lost/expired challenge recovers via requirements + resend (new challenge). The `verification_session_token` cookie is retired from booking. |
| F6  | Routes                   | Keep: `contact`, `contact/verify-mobile`, `contact/sign-in`, `success`. Delete from booking: `contact/sign-up`, `contact/verify-email`, `contact/collect-email`, `contact/collect-mobile`.                                                                                                           |
| F7  | Sign-in link             | Unconditional "Har du allerede en konto? Logg inn" on the contact form (shown to everyone — leaks nothing). Carries sessionId/returnUrl; after login, routes back into the authenticated attach path.                                                                                                |
| F8  | Stepper                  | "Bruker" renamed "Kontakt". The step is honestly two screens: details → SMS code.                                                                                                                                                                                                                    |
| F9  | Post-flow states         | Success page renders off `isReturning` + `accountStatus`: completion card for GUEST only (driven by `completionToken`), "Velkommen tilbake" for returning users, nothing account-flavored for FULL.                                                                                                  |
| F10 | Recognition reveal       | Never before OTP. Identical form → code path for known and unknown mobiles. "Velkommen tilbake, {name}" appears only after verify succeeds. No `EXISTING_USER_FOUND`-style state anywhere.                                                                                                           |
| F11 | Hotfix                   | The two old-flow bugs behind the complaint are fixed immediately, ahead of the rework (§6).                                                                                                                                                                                                          |
| F12 | Backend delta            | One addition to backend rev 3.4: `/requirements` returns `displayName` (given name) when `session.userId` is set (§7). Everything else in this plan is frontend-only.                                                                                                                                |
| F13 | Step order               | Reordered to employee → services → time → **Kontakt** → overview. Identity is asked at the conversion-optimal moment, after the user has invested in selections. Selection steps require only a valid session; identity is required only from Kontakt onward.                                        |
| F14 | Provider login placement | Google/OAuth buttons are removed from the contact form; they live only behind the "Logg inn" link (sign-in page). One primary action per screen: mobile + SMS.                                                                                                                                       |

## 2. Route and state map

### 2.1 Routes after rework (order per F13)

```
/booking/public/appointment/session/employee                 step 1 — session only
/booking/public/appointment/session/select-services          step 2 — session only
/booking/public/appointment/session/select-time              step 3 — session only
/booking/public/appointment/session/contact                  step 4 "Kontakt" — state-aware screen
/booking/public/appointment/session/contact/verify-mobile    code entry (?challengeId=)
/booking/public/appointment/session/contact/sign-in          kept; booking-context framing
/booking/public/appointment/session/overview                 step 5 — requires identity DONE
/booking/public/appointment/success                          + completion card for GUEST
```

Guard scope after reorder: employee/services/time require only a valid appointment session —
no identity. Kontakt requires selections complete (deep link to contact without selections →
redirect to first incomplete selection step). Overview/submit require identity `DONE`
(`requireBookingReady`). Because time is now selected before identity, the existing
slot-taken-at-submit handling carries slightly more traffic — the recovery (back to time
selection, everything else intact) is already specified and unchanged.

Deleted routes: `contact/sign-up`, `contact/verify-email`, `contact/collect-email`,
`contact/collect-mobile`. Account creation happens post-booking (completion card → account
routes) or on the normal account pages — never inside the booking flow.

### 2.2 UI states (derived per F3, exactly one per load)

| State         | Condition                                                                                     | Screen                                                                                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CONTINUE_AS   | Valid auth tokens                                                                             | "Fortsett som {name} — ikke deg?" bar. Primary: continue → attach (§4.5 backend) → overview. Secondary: "ikke deg?" → CONTACT_FORM.                                                               |
| RESUME        | `session.userId` set, `nextStep = DONE`, no tokens                                            | Resume card: "Kontaktinformasjonen din er bekreftet" + `displayName` + masked mobile. Primary: "Fortsett til booking" → overview. Secondary: "Endre kontaktinfo" → CONTACT_FORM.                  |
| CONTACT_FORM  | No user attached (or user chose change/switch)                                                | Fields: Fornavn, Etternavn, Mobilnummer, E-post (valgfritt). Primary: "Fortsett til SMS-bekreftelse". Small link: "Har du allerede en konto? Logg inn". No provider buttons on this screen (F14). |
| VERIFY_MOBILE | `nextStep = VERIFY_MOBILE`                                                                    | Code screen (§3).                                                                                                                                                                                 |
| (forwarding)  | `nextStep = DONE` and current route is a contact route the user didn't navigate to explicitly | Redirect to overview.                                                                                                                                                                             |

A signed-in user with missing/unverified mobile lands on CONTACT_FORM pre-filled (this replaces
collect-mobile) and continues into the same challenge machinery.

## 3. Screens and copy

### 3.1 Contact form

- Title: `Kontaktinformasjon`
- Description: `Vi bruker mobilnummeret ditt til å bekrefte bookingen og sende viktig
informasjon om timen. E-post er valgfritt.`
- Email helper: `Valgfritt. Legg inn e-post hvis du også vil motta bekreftelse på e-post.`
- Primary: `Fortsett til SMS-bekreftelse`
- Link: `Har du allerede en konto? Logg inn`
- Submit → `POST /identify` → navigate to verify-mobile with `challengeId` in state.

### 3.2 Verify mobile

- Title: `Bekreft mobilnummeret ditt`
- Shows the number: `Vi har sendt en kode til {maskedMobile}` (e.g. `+47 ••• 81`).
- 6-digit input: auto-focus, SMS autofill (`autocomplete="one-time-code"`), auto-submit on the
  sixth digit.
- Primary: `Bekreft kode`
- Secondary: `Send SMS på nytt` (countdown matching backend cooldown), `Feil nummer? Endre` →
  contact form.
- Error states: wrong code (generic message, attempts remaining implicit), challenge
  expired/exhausted → message + resend as the recovery action, rate-limited → calm wait message.
- On success: store tokens, then per response — `isReturning=false` → continue silently;
  `isReturning=true` → brief "Velkommen tilbake, {name}" confirmation → overview.
- Lost `challengeId` (refresh): loader sees VERIFY_MOBILE, renders the screen with resend as the
  primary recovery. No dead ends, no cookie dependency.

### 3.3 Sign-in (kept)

- Framing line added: `Logg inn for å fortsette bookingen din.`
- Carries sessionId/returnUrl; after successful password/OAuth login, routes back to the
  contact loader, which resolves CONTINUE_AS → attach → overview.

### 3.4 Success page

- Always: appointment details.
- `accountStatus = GUEST`: skippable completion card — `Lagre detaljene dine for raskere
booking neste gang` → add email / set password / link Google (uses `completionToken`).
- Returning user: `Velkommen tilbake`-flavored confirmation.
- `accountStatus = FULL`: no account prompts at all.

## 4. Resilience rules

1. `requireAuthenticatedBookingFlow` → renamed `requireBookingReady`; checks `/requirements`,
   not auth user-status. On transient fetch failure: keep the session cookie, redirect to
   `/contact` (cookie intact) or render retry. Clear the cookie only on backend-confirmed
   stale/invalid session (F4).
2. No polling anywhere. The email waiting-screen pattern is deleted with the email step; SMS
   verification is user-driven (type the code).
3. Back/refresh from any contact route re-runs the loader contract and self-corrects (F3). Back
   from verify-mobile after success → requirements says DONE → forwarded to overview, never a
   "new user" state.
4. Overview's "Endre" under contact → `/contact`, which now renders the RESUME card, not the
   identity hub.
5. Frontend never sees or handles: `verificationSessionToken`, `COLLECT_EMAIL`, `VERIFY_EMAIL`,
   pending-session-user semantics. If any of these appear in booking code after the rework,
   that's a defect.

## 8. Codebase consistency audit

This section compares the plan against the current frontend codebase. These are the
inconsistencies and hidden migration dependencies that must be resolved while implementing the
plan.

### 8.1 Session entry still routes to contact first

Plan says the new order is employee → services → time → Kontakt → overview.

Current code:

- `app/routes/booking/public/appointment/session/booking.public.appointment.session.route.tsx`
  creates or reuses the appointment session and always redirects to `routes.contact`.

Required adjustment:

- Change the session entry loader to redirect to the first selection step, probably
  `routes.employee`, after creating/reusing a valid session.
- Preserve existing company/theme/session reset handling.
- Re-check all tests in `app/routes/booking/public/appointment/session/booking.session.loader.test.ts`,
  because they currently expect redirects to contact.

### 8.2 Selection steps currently require identity

Plan says employee/services/time should require only a valid appointment session.

Current code:

- `employee/...route.tsx`
- `select-services/...route.tsx`
- `select-time/...route.tsx`
- `overview/...route.tsx`

All four currently call `requireAuthenticatedBookingFlow`, which requires `session.userId` and
auth status. That means the current code cannot support the planned order without a new guard.

Required adjustment:

- Introduce a session-only guard for employee/services/time.
- Keep a stricter `requireBookingReady` guard for overview/submit.
- Update every loader and action in employee/services/time to use the session-only guard.
- Update back links and error redirects that currently assume contact is the previous step.

### 8.3 Contact does not currently enforce completed selections

Plan says deep-linking to Kontakt before employee/services/time are complete should redirect to
the first incomplete selection step.

Current code:

- `contact/booking.public.appointment.session.contact.route.tsx`
- `contact/booking.public.appointment.session.contact.layout.tsx`

Neither loader checks `selectedProfileId`, `selectedServices`, or `selectedStartTime`.

Required adjustment:

- Add a frontend helper that inspects `AppointmentSessionDto` and returns the first incomplete
  pre-contact route.
- Use it in every contact route loader, including verify-mobile and sign-in.
- Be careful with single-profile auto-select: employee currently auto-selects and redirects to
  services when only one profile exists.

### 8.4 Stepper uses old contact-first order and backend step IDs

Plan says "Bruker" becomes "Kontakt" and moves after time.

Current code:

- `app/routes/booking/public/_utils/booking.step-navigation.ts`

Current `BOOKING_STEPS` order is:

1. contact
2. employee
3. select-services
4. select-time
5. overview

It also maps backend step IDs/order from `session.steps`, where generated
`AppointmentSessionStepDto.appointmentSessionStepId` currently includes `ADD_USER`,
`SELECT_SERVICES`, `SELECT_PROFILE`, `SELECT_START_TIME`, `OVERVIEW`.

Required adjustment:

- Reorder `BOOKING_STEPS`.
- Rename `contact` display name from `Bruker` to `Kontakt`.
- Confirm backend `session.steps` order changes too, or stop trusting backend `order` directly
  for UI step order.
- Update tests using step order/progress assumptions.

### 8.5 Current generated `/requirements` contract is not the planned contract

Plan says `/requirements` is the single resolver and frontend never handles `COLLECT_EMAIL` or
`VERIFY_EMAIL`.

Current generated API already has:

- `PublicAppointmentSessionController.getAppointmentSessionRequirements`
- URL: `/booking-service/public/appointment-session/{sessionId}/requirements`
- DTO: `PublicSessionRequirementsDto`

Current DTO fields:

- `needsUser`
- `needsEmail`
- `needsMobile`
- `nextStep: 'COLLECT_MOBILE' | 'VERIFY_MOBILE' | 'COLLECT_EMAIL' | 'VERIFY_EMAIL' | 'DONE'`

Missing from current generated DTO:

- `sessionId`
- `userId`
- `displayName`
- `maskedMobile`
- `challengeId`
- `expiresAt`
- `resendAvailableAt`
- guest-state enum such as `CONTACT_FORM | VERIFY_MOBILE | DONE`

Required adjustment:

- Backend/OpenAPI must change more than only adding `displayName`.
- Frontend cannot implement the planned state machine cleanly against the current generated
  requirements DTO.
- After backend changes, regenerate API clients and update the plan if final enum names differ.

### 8.6 New identify/challenge/completion APIs are not in generated client yet

Plan depends on:

- `POST /identify`
- verify mobile by `challengeId`
- resend mobile challenge by `challengeId` or session
- submit returning `accountStatus` and `completionToken`
- `/public/account/complete`

Current generated booking client does not expose identify/challenge/completion endpoints. The
only matching generated public session identity helpers are existing session/status/session
selection endpoints.

Required adjustment:

- Backend/OpenAPI implementation must land before frontend can wire this flow without hand-written
  types.
- Add explicit frontend tasks for API regeneration and replacing old `AuthController` calls.

### 8.7 Contact route map still includes deleted routes

Plan says delete booking routes:

- `contact/sign-up`
- `contact/verify-email`
- `contact/collect-email`
- `contact/collect-mobile`

Current references remain in:

- `app/lib/routing/booking/booking.routes.ts`
- `app/routes/booking/public/_utils/booking.route-map.ts`
- `app/lib/route-meta.ts`
- `app/routes/booking/public/appointment/session/booking.pending-submission-ui.test.ts`
- `app/routes/booking/public/appointment/session/contact/booking.contact-auth.routes.matrix.test.ts`
- `app/routes/booking/public/appointment/session/contact/_utils/auth.utils.test.ts`
- `app/routes/booking/public/appointment/session/contact/verify-mobile/...route.test.ts`

Required adjustment:

- Delete route files and route tree entries together.
- Remove deleted route keys from `BookingRouteKey` and `BOOKING_ROUTE_IDS`.
- Update or delete route-meta overrides for removed booking routes.
- Update tests that read deleted files directly.
- Decide whether deleted URLs should 404 or redirect to contact; if redirect is desired, keep
  explicit redirect route modules rather than deleting them outright.

### 8.8 Plan has an internal contradiction about `challengeId`

Decision F5 says `challengeId` travels as a URL query param on verify-mobile.

Section 3.1 says:

- `Submit → POST /identify → navigate to verify-mobile with challengeId in state.`

Required adjustment:

- Use URL query param consistently:
  - `/contact/verify-mobile?challengeId=...`
- Avoid React Router navigation state for challenge persistence, because state does not survive
  direct URL entry and is weaker for refresh recovery.

### 8.9 Current verify-mobile still depends on old auth verification cookie

Plan says `verification_session_token` is retired from booking.

Current code:

- `contact/verify-mobile/...route.tsx`
- `routes/api/auth/verify-mobile/auth.verify-mobile.api-route.ts`
- `routes/api/auth/resend-verification/mobile/...api-route.ts`

These read `VerificationTokenService.readVerificationToken(request)` and use
`AuthController.verifyMobile`/resend verification APIs.

Required adjustment:

- Replace the booking verify-mobile route with session + requirements + challengeId logic.
- Replace `/api/auth/verify-mobile` usage in booking with booking-specific verify challenge
  action.
- Keep the auth verification-token service for the non-booking auth flow if still needed.

### 8.10 Current email verification is used by both booking and auth flows

Plan says booking deletes email verification, but the codebase also has normal auth routes:

- `/auth/verify-email`
- `/auth/check-email`
- `/auth/collect-email`
- `/auth/collect-mobile`

Booking-specific email route files can be deleted, but shared helpers are still imported by
auth routes.

Required adjustment:

- Do not delete `VerificationTokenService` globally unless the standalone auth flow is also
  migrated.
- If retiring it "from booking", move booking away from it and leave auth routes intact.
- Watch imports from `routes/auth/*` before removing shared helper files.

### 8.11 Success page currently cannot render planned account states

Plan says success renders from:

- `isReturning`
- `accountStatus`
- `completionToken`

Current code:

- `overview` action redirects to success with only `companyId` and `appointmentId`.
- `success` loader fetches company by `companyId` and appointment by `appointmentId`.
- Success UI always includes `Se mine bookinger`, even though that route is authenticated.
- Success copy says `Bekreftelse sendt til e-post`, which conflicts with guest/mobile-first
  booking where email is optional.

Required adjustment:

- Decide where `accountStatus` and `completionToken` are carried:
  - query params
  - server-side session/result lookup
  - appointment details endpoint
- Avoid putting sensitive completion tokens in URLs if backend treats them as secrets.
- Rework success CTA logic for guest users who may not have an account.
- Fix email-specific success copy for email-optional bookings.

### 8.12 Existing attach-user API is not safe enough as the planned attach path

Current code has:

- `/api/public/booking/session/attach-user`
- It accepts form `sessionId` and `userId`, then calls `setPendingAppointmentSessionUser`.

Plan says the sign-in detour returns to an authenticated attach path.

Required adjustment:

- Do not reuse the current public attach-user API as-is for the final plan unless it verifies
  the authenticated user server-side.
- Prefer an attach path that derives user ID from auth cookies/session, not arbitrary form data.
- Remove or lock down the current API route if it becomes obsolete.

### 8.13 Current form/schema expects 8-digit local mobile numbers

Plan examples include masked international numbers like `+47 ••• 81`.

Current code:

- `submit-contact.form.schema.ts` validates `mobileNumber.length(8)`.
- Sign-up/collect-mobile fields are plain `tel`, but backend examples and existing data use

Required adjustment:

- Decide whether the frontend input remains Norwegian 8-digit only or supports country code.
- Make masking/normalization explicit.
- Align identify API request format with existing backend expectations.

### 8.14 "No polling anywhere" requires deleting only booking polling

Plan says no polling anywhere.

Current booking email verification polls `/api/auth/user-status` every second.

Required adjustment:

- Delete booking email polling with the deleted booking email route.
- Do not interpret this as a global ban on polling in unrelated app areas unless separately

### 8.15 Current tests contain source-string assertions tied to deleted code

Several tests read source files and assert exact strings:

- contact auth matrix tests
- verify-mobile route tests

Required adjustment:

### 8.16 Current selected-step navigation and back links assume contact-first

### 8.18 Overview submit error recovery is not as specific as the plan states

## 9. Tests

**Loader contract**: each contact route redirects to the canonical route for the resolved
state; refresh on every contact route is a no-op; direct-URL entry to a deleted route 404s or
redirects to contact.

**Step order (F13)**: employee/services/time load with a bare session (no identity); deep link
to contact without completed selections redirects to the first incomplete selection step;
overview without identity DONE redirects to contact; slot-taken-at-submit returns to time
selection with contact state intact.

**Challenge param (F5)**: verify-mobile with a valid `?challengeId=` renders the code screen;
with a missing/expired param it renders with resend as primary recovery (no dead end, no extra
SMS sent automatically).

**States**: tokens → CONTINUE_AS; session.userId + DONE + no cookies → RESUME with displayName;
nothing → CONTACT_FORM; VERIFY_MOBILE → code screen; DONE on a contact route → forwarded.

**Recognition**: form → code path identical for known/unknown mobile (no conditional UI on the
identify response); "Velkommen tilbake" only after verify; no completion card for FULL.

**Resilience**: transient requirements failure preserves the session cookie; lost challengeId
recovers via resend; back from verify-mobile after success lands on overview; overview "Endre"
shows RESUME, never sign-up.

**Code screen**: shows masked number; autofill/auto-submit; resend countdown; expired/exhausted
recovery; rate-limit message.

**Sign-in detour**: login link → password login → returns to session → attach → overview.

**Success page**: three states render correctly; completion card only when `completionToken`
present.

**Hotfix (old flow, ships first)**: the two regression tests in §6.
