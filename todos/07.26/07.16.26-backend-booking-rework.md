## 1. Backend Goal

Support a guest-first public booking flow where booking identity is resolved by backend state, not frontend inference.

The backend must provide one canonical requirements resolver and guest verification flow so the frontend can render exactly one state at a time:

- continue as authenticated user
- resume a verified session user
- enter contact details
- verify mobile
- continue to overview

No email verification should be required inside the public booking flow.

---

## 2. Required API Surface

The frontend rework depends on backend rev 3.4 concepts referenced in the frontend plan:

- `GET /public/appointment-session/{sessionId}/requirements`
- `POST /public/appointment-session/{sessionId}/identify`
- mobile challenge creation/resend
- mobile challenge verification
- authenticated attach path
- appointment submit returning completion state
- `POST /public/account/complete` or equivalent post-booking account completion endpoint

Exact backend route names may differ in the backend service. The contract below is the required behavior.

## 3. Requirements Resolver

### Endpoint

`GET /public/appointment-session/{sessionId}/requirements`

### Purpose

Single source of truth for frontend booking contact state.

The frontend must not derive identity state from auth cookies, old `nextStep` values, pending-user behavior, or verification-token cookies. It should call this resolver and route from the returned state.

### Required behavior

- Accepts appointment `sessionId`.
- Validates that the session exists and is usable.
- Returns the next required booking identity/contact state.
- Does not require full auth for anonymous/guest sessions.
- Does not reveal whether a mobile number belongs to an existing user before OTP verification.
- Never returns email verification as a public booking requirement.
- Is idempotent across refresh/back/forward navigation.
- Returns enough safe display data to render resumable booking states.

### Required response fields

At minimum:

- `nextStep`
  - Expected frontend states:
    - `CONTACT_FORM`
    - `VERIFY_MOBILE`
    - `DONE`
  - If backend uses a different enum, it must be mapped cleanly and documented.
- `sessionId`
- `userId`, when attached and safe to expose for this session.
- `maskedMobile`, when a user/contact mobile exists and may be displayed.
- `displayName`, when `session.userId` is set.
- `challengeId`, when the current state is `VERIFY_MOBILE` and an active challenge exists.
- challenge timing metadata when relevant:
  - `expiresAt`
  - `resendAvailableAt`
  - `remainingAttempts`, if the backend wants the UI to show it.

### Explicit delta from frontend plan

Add to requirements response:

- `displayName`
  - Given name only.
  - Returned only when `session.userId` is set.
  - Used for the RESUME card.
- `maskedMobile`
  - Returned only when `session.userId` is set or the user is already in a verification state where the number is safe to display.
  - Example display: `+47 ••• 81`.

Safety rationale:

- The appointment session ID is an unguessable capability held by the person who started the session.
- Do not expose full mobile or unnecessary personal data.
- Do not return `displayName` or `maskedMobile` for anonymous sessions with no attached user.

### Required tests

- Anonymous session returns contact form state and no `displayName`.
- Session with `userId` and completed verification returns `DONE`, `displayName`, and `maskedMobile`.
- Session with `userId` and active mobile challenge returns `VERIFY_MOBILE`, `challengeId`, and masked mobile.
- Session without a valid ID returns a clear stale/invalid session response.
- Transient internal dependency failures are distinguishable from stale/invalid session.
- Response never includes email verification as a required booking step.
- Existing-user recognition is not leaked before OTP verification.

## 4. Identify Contact

### Endpoint

`POST /public/appointment-session/{sessionId}/identify`

### Purpose

Create or resolve the booking contact and start the SMS verification path without exposing whether the mobile belongs to an existing user.

### Request fields

- `givenName`
- `familyName`
- `mobileNumber`
- `email`, optional

### Required behavior

- Mobile number is required.
- Email is optional.
- No password is required inside public booking.
- No email verification is started or required inside public booking.
- Known and unknown mobile numbers follow the same external response shape before OTP verification.
- If a user/contact is created or resolved, attach it to the appointment session as pending/guest identity as appropriate.
- Start or reuse an SMS challenge.
- Return `challengeId` for the frontend verify route query param.
- Return masked mobile and challenge timing metadata.

### Required response shape

At minimum:

- `nextStep: VERIFY_MOBILE`
- `challengeId`
- `maskedMobile`
- `expiresAt`
- `resendAvailableAt`, when cooldown applies

Optional after safe verification only:

- `isReturning`
- `displayName`

### Required tests

- New mobile and existing mobile produce the same pre-verification UI-safe response.
- Email is accepted but does not create an email verification requirement.
- Missing/invalid mobile returns validation error.
- Challenge reuse/cooldown behavior is stable and documented.
- Appointment session is not lost when identify fails validation.

## 5. Mobile Challenge Verification

### Endpoint

Verify SMS code for a booking challenge.

Suggested contract:

`POST /public/appointment-session/{sessionId}/verify-mobile`

or existing backend equivalent, as long as frontend does not depend on the old `verification_session_token` cookie.

### Request fields

- `challengeId`
- `code`

### Required behavior

- Validate challenge belongs to the appointment session.
- Validate code.
- On success:
  - mark mobile verified
  - attach/confirm user on appointment session
  - issue auth tokens if that is part of the backend model
  - return `nextStep: DONE`
  - return `isReturning` only after successful verification
  - return `displayName` only after successful verification or for an already attached session user
- On failure:
  - wrong code returns generic error
  - expired/exhausted challenge returns recoverable error
  - rate-limited state returns cooldown metadata
- Do not require or return email verification in booking.

### Required response fields

Success:

- `nextStep: DONE`
- `isReturning`
- `displayName`, if available and safe
- auth tokens/cookie data, if required by current auth model

Failure:

- stable error code
- localized or mappable message
- `resendAvailableAt`, when rate limited
- `remainingAttempts`, if supported

### Required tests

- Correct code verifies mobile and sets booking identity to done.
- Wrong code does not reveal account existence.
- Expired challenge can be recovered by resend.
- Exhausted challenge can be recovered by resend/new challenge.
- Challenge cannot be used across another session.
- Successful verification never routes to email verification.

## 6. Resend Mobile Challenge

### Endpoint

Resend or create a new SMS challenge for the current appointment session.

Suggested contract:

`POST /public/appointment-session/{sessionId}/mobile-challenge/resend`

or backend equivalent.

### Required behavior

- Requires valid appointment session.
- Works when `challengeId` is missing, expired, or exhausted.
- Respects backend cooldown/rate limits.
- Returns a fresh or active `challengeId`.
- Returns masked mobile and timing metadata.
- Does not send email.

### Required response fields

- `challengeId`
- `maskedMobile`
- `expiresAt`
- `resendAvailableAt`

### Required tests

- Missing challenge ID can recover via resend when session has pending mobile.
- Cooldown returns stable metadata and does not create uncontrolled SMS sending.
- Expired challenge produces a new usable challenge.
- Resend does not expose whether the number belongs to an existing full account.

## 7. Authenticated Attach Path

### Purpose

Support the sign-in detour from public booking.

Frontend flow:

1. User clicks `Har du allerede en konto? Logg inn`.
2. User signs in through existing auth/OAuth.
3. Backend attaches the authenticated user to the appointment session.
4. Requirements resolver returns `DONE` or the next required contact state.

### Required behavior

- Accept a valid auth user and appointment session.
- Attach authenticated user to the appointment session.
- Return requirements-compatible state after attach.
- If authenticated user lacks verified mobile and mobile is required, return contact/verify mobile state.
- If authenticated user is ready, return `DONE`.

### Required tests

- Full authenticated user attaches and requirements returns `DONE`.
- Authenticated user missing mobile is sent through the same contact/SMS path.
- Switching users does not leak prior session user details.

## 8. Submit Appointment and Completion Token

### Endpoint

Existing appointment submit endpoint:

`POST /public/appointment-session/{sessionId}/submit`

or backend equivalent.

### Required behavior

- Requires booking identity requirements to be `DONE`.
- Submits appointment.
- Returns appointment ID.
- Returns account completion metadata for guest users only.
- Does not require account creation before booking.

### Required response fields

- `appointmentId`
- `accountStatus`
  - `GUEST`
  - `RETURNING`
  - `FULL`
- `completionToken`, only when `accountStatus = GUEST` and account completion is allowed.

### Required tests

- Guest submit returns appointment ID and completion token.
- Returning user submit returns no guest completion prompt data unless intentionally supported.
- Full account submit returns no completion token.
- Slot conflict preserves session and allows frontend to return to time selection.
- Submit never sends user back into contact/registration after successful appointment creation.

---

## 9. Public Account Completion

### Endpoint

`POST /public/account/complete`

or backend equivalent.

### Purpose

Let guest users optionally save account details after the appointment is booked.

### Required behavior

- Uses `completionToken`.
- Allows adding email, setting password, or linking Google/OAuth depending on backend capabilities.
- Is optional and post-booking only.
- Does not affect appointment success state if skipped.

### Required tests

- Valid completion token can complete account.
- Expired/invalid token fails safely.
- Completion cannot be used to access another user's appointment/account.
- Skipping completion leaves appointment intact.

## 10. Session Failure Semantics

Backend should clearly distinguish:

- stale/invalid appointment session
- transient dependency failure
- validation failure
- rate limiting
- challenge expired/exhausted
- unauthorized authenticated attach

Frontend requirement:

- Clear appointment session only when backend explicitly reports stale/invalid session.
- Do not clear session on transient requirements/auth/status failures.

Backend/API requirement:

- Return stable error codes/statuses so frontend can make that distinction.

Suggested error codes:

- `SESSION_NOT_FOUND`
- `SESSION_EXPIRED`
- `REQUIREMENTS_UNAVAILABLE`
- `CHALLENGE_EXPIRED`
- `CHALLENGE_EXHAUSTED`
- `CHALLENGE_RATE_LIMITED`
- `INVALID_CODE`
- `CONTACT_VALIDATION_FAILED`

## 12. Backend Acceptance Criteria

- [ ] Public booking can be completed as a guest with verified mobile and optional email.
- [ ] No email verification step is returned for booking.
- [ ] No password/account creation is required before appointment submission.
- [ ] Requirements endpoint is the single canonical state resolver.
- [ ] Requirements response includes `displayName` and `maskedMobile` only when safe.
- [ ] Known vs unknown mobile recognition is never revealed before OTP verification.
- [ ] `challengeId` can be carried in URL and recovered via requirements/resend.
- [ ] Mobile challenge verification is tied to the appointment session.
- [ ] Transient backend failures are distinguishable from stale sessions.
- [ ] Appointment submit returns guest completion metadata only after successful booking.
- [ ] OpenAPI/client generation includes all new or changed contracts.
