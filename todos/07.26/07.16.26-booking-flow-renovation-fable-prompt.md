# Public booking flow — route renovation plan (rev 4)

Status: implementation plan, companion to frontend contact plan rev 2 and backend plan rev 3.4
Rev 4 (consistency): `bookingApi` wrapper removed everywhere — routes call the generated SDK
directly; concrete SDK method names in every route spec; select-time action unified on PRG
redirect-to-self; CONTINUE_AS attach named (`setPendingAppointmentSessionUser`) with nextStep
branching; `logBooking` introduced in commit 1, commit 11 becomes the wrapper-deletion sweep.
Rev 2: Appendix A added — full reference implementation of the select-time route (commit 1),
based on review of the current route file; three findings from that review folded into §6.
Rev 3 (codebase/SDK validation): helper names labeled as renovation targets with current→target
mapping; concrete generated-SDK method names; contact action handles all three identify
outcomes; verify-mobile resend/recovery corrected to the actual DTOs; exact cleanup targets for
the verification-token stack; §4 replaced with the verified DTO contract.
Principle: every route file answers five questions at a glance — what loads, what the user can
click, what submits, what backend call happens, where it redirects. Backend session is the only
source of truth. Boring on purpose.

---

## 1. Direct answer to the design question

**Mostly yes.** "Route owns its own logic" is not just acceptable for this flow — it is the
intended design of React Router framework mode. The route module (loader + action + component
in one file) is the framework's unit of composition; actions redirect; loader data revalidates
automatically after every action, so "click a slot → session updates → UI reflects session"
requires zero client state. Multi-step transactional flows built on plain loaders/actions/Forms
are a documented, library-free pattern that holds up well at this complexity level.

The narrow exceptions — the only shared code that may influence flow, each for a stated reason:

| Shared thing                                                | Why it's allowed                                                                                                                                   | Hard rule                                                                                                                                             |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getBookingSession(request)`                                | Reading the session cookie, fetching the session, handling stale/missing is a data concern, identical everywhere. Duplicating it 7× invites drift. | Returns `session` or throws `redirect(...)`. Never clears the cookie on transient fetch failure (only on backend-confirmed stale). No other behavior. |
| Generated SDK client (`PublicAppointmentSessionController`) | Routes call it directly — there is NO wrapper layer.                                                                                               | Logging happens via flat `logBooking` lines in the route (§7), never inside a wrapper.                                                                |
| `bookingRoutes` path constants                              | Typo-proof hrefs.                                                                                                                                  | A flat object of strings. No functions, no logic.                                                                                                     |
| `BookingStepLayout`                                         | Visual shell: header, stepper, content slot, footer slot.                                                                                          | Receives children only. Owns zero buttons, zero forms, zero navigation.                                                                               |
| Small display components (slot grid item, price row)        | Rendering only.                                                                                                                                    | No submit, no navigate, no props that pass navigation behavior through layers.                                                                        |

Everything else the route owns. Explicit rule set:

**Naming — these helpers are renovation targets, not existing code.** Current → target:
`getBookingRouteMap()` (booking.route-map.ts) → `bookingRoutes` flat constants object;
`requireBookingSession()` / `requireBookingReady()` (booking.require-authenticated-flow.server.ts)
→ `getBookingSession` / `requireBookingReady` refactored to carry the never-clear-on-transient
rule; `withBookingFlowLog()` + `withBookingBackendCall()` (booking-flow-log.server.ts) →
deleted, replaced by `logBooking` (flat, behavior-free, §7); `BookingStepTemplate` →
`BookingStepLayout` (same component, stripped to a children-only shell). Timing: `logBooking`
(a ~10-line helper) is introduced in commit 1 because select-time uses it; `bookingRoutes` and
`BookingStepLayout` in commit 2; the guard refactor in commit 7. Earlier commits may use the
current names for what isn't yet refactored.

SDK: routes call the generated client directly — `PublicAppointmentSessionController.`
`getAppointmentSessionRequirements`, `identifyAppointmentSessionUser`,
`verifyAppointmentSessionUserMobile`, `resendAppointmentSessionMobileChallenge`,
`submitAppointmentSessionStartTime`, `submitAppointmentSession`.

- Every form is a visible `<Form method="post">` inside the route component. **No hidden forms,
  no `form="id"` attribute linking buttons to forms elsewhere in the tree.**
- Multiple intents in one action are distinguished by the submit button's `name`/`value` — the
  standard pattern — and the `switch` on intent lives at the top of the action, readable in one
  screen.
- Every redirect is a `redirect(bookingRoutes.x)` line inside the route's own loader or action.
- Back and Continue are rendered by the route, in the layout's footer slot, as plain elements:
  Back is always a `<Link>`; Continue is a `<Link>` when the prerequisite already exists in the
  session, or a submit button in the route's visible form when submitting is what advances.
- No client-side state for anything the session knows. `useState` is allowed only for pure
  input ergonomics (e.g., the OTP input focus), never for selections.

**Delete:** `BookingBottomActionBar` as a behavior-carrying component (a purely visual footer
container may remain inside `BookingStepLayout`), the hidden continue forms, the
`intent=continue` round-trips where a `<Link>` suffices, and `booking-flow-log.server.ts` if it
wraps behavior (replace per §7). The select-time bug class — button in one file, form in
another, intent in a third, redirect in a fourth — becomes unwritable under these rules.

## 2. The flow (fixed sequence, backend-guarded)

```
company/service context → employee → select-services → select-time → contact
                                                     → contact/verify-mobile (when required)
                                                     → overview → success
```

Guard ladder (each step's loader validates its own prerequisites and redirects backward if
missing — this is the safety net that makes Continue-as-Link safe):

| Route           | Loader requires                                    | If missing, redirect to                  |
| --------------- | -------------------------------------------------- | ---------------------------------------- |
| employee        | valid session                                      | booking start                            |
| select-services | session + selectedProfileId (when profiles apply)  | employee                                 |
| select-time     | session + selected services                        | select-services                          |
| contact         | session + selectedStartTime                        | select-time                              |
| verify-mobile   | contact prerequisites + `nextStep = VERIFY_MOBILE` | contact (or forward to overview if DONE) |
| overview        | identity `DONE` (via requirements)                 | contact                                  |
| success         | appointmentId param                                | booking start                            |

Back navigation: **fixed sequence, explicit `<Link>`s** (employee ← services ← time ← contact ←
overview). Browser back also works safely because every loader re-validates and self-corrects —
but the rendered Back button never relies on history.

## 3. Route-by-route specification

Each route follows the same skeleton; only the differences are listed.

### 3.1 employee

- Loader: `getBookingSession` → fetch profiles → return `{ session, profiles }`.
- Component: profile cards inside one visible Form; each card is a submit button
  `name="profileId"`. Back: Link to company page.
- Action: read `profileId` → `PublicAppointmentSessionController.selectAppointmentSessionProfile`
  → `redirect(selectServices)`.

### 3.2 select-services

- Loader: session + services for selected profile.
- Component: one visible Form with checkboxes `name="serviceIds"`; Continue is the form's
  submit button (selection and continuation are the same act here). Back: Link to employee.
- Action: validate ≥1 service →
  `PublicAppointmentSessionController.selectAppointmentSessionProfileServices` →
  `redirect(selectTime)`.

### 3.3 select-time — the decided pattern

- Loader: session + available slots. Return `{ session, slots, selectedStartTime }` (selected
  time comes from the session, never client state).
- Component: one visible Form wrapping the slot grid. **Each slot is a submit button
  `name="startTime" value={iso}`.** Clicking a slot posts; the action saves; revalidation
  re-renders with the backend-selected slot highlighted. No fetchers, no optimistic state.
- **Continue is a plain `<Link to={contact}>` rendered only when `session.selectedStartTime`
  exists** (disabled/hidden otherwise). No continue intent, no hidden form, no second action
  branch. If the Link ever renders wrongly, contact's loader bounces back — defense in depth.
- Action: read `startTime` → validate →
  `PublicAppointmentSessionController.submitAppointmentSessionStartTime` →
  `redirect(bookingRoutes.selectTime)` — PRG back to self; the reload shows the
  backend-selected slot. Matches Appendix A exactly. The action has exactly one intent.
- Back: Link to select-services.

### 3.4 contact (per frontend plan rev 2, F-decisions apply)

- Loader: session (requires selectedStartTime) + `GET /requirements` → derive exactly one of:
  CONTINUE_AS (valid tokens) / RESUME (`session.userId` + DONE) / CONTACT_FORM / VERIFY_MOBILE
  (redirect to the verify route). **Contact never auto-forwards to overview** — DONE renders the
  RESUME card ("Kontaktinformasjonen din er bekreftet", primary Link → overview, secondary
  "Endre kontaktinfo"). This makes Back-from-overview land somewhere sensible instead of
  bouncing.
- Component: fields Fornavn, Etternavn, Mobilnummer. **E-post is behind a small toggle link
  "Legg til e-post (valgfritt)"** — not shown as an open field, never prompted, never blocking
  (satisfies "do not prompt unless the user chooses"). Primary submit: "Fortsett til
  SMS-bekreftelse". Small unconditional link: "Har du allerede en konto? Logg inn". No provider
  buttons (F14). Back: Link to select-time.
- Action: validate name + mobile syntax → `identifyAppointmentSessionUser` → branch on the
  response's `nextStep`: `VERIFY_MOBILE` → `redirect(verifyMobile + "?challengeId=" +
response.challengeId)`; `DONE` → `redirect(overview)` (e.g. signed-in user with already
  verified mobile); missing/other or error → stay on contact with the error message.
- CONTINUE_AS attach: its own intent in this action (`intent="attach"`) →
  `PublicAppointmentSessionController.setPendingAppointmentSessionUser({ path: { sessionId } })`
  → branch on returned `nextStep`: `DONE` → overview; `VERIFY_MOBILE` → verify-mobile (with the
  challengeId the response/requirements provides); otherwise → stay on contact with error.

### 3.5 contact/verify-mobile

- Loader: `getAppointmentSessionRequirements`; if `DONE` → `redirect(overview)` (already
  verified — never ask again); if `CONTACT_FORM` → `redirect(contact)`. Read `challengeId`
  from the URL; **if the URL param is missing but `requirements.challengeId` is present,
  redirect to self with that challengeId** — never bounce the user back to contact when a live
  challenge exists. Only when neither exists does the screen render with resend as the primary
  recovery. Use `maskedMobile` and the resend/cooldown fields from requirements for display.
- Component: shows the masked number ("Vi har sendt en kode til +47 ••• 81"); 6-digit input,
  `autocomplete="one-time-code"`, auto-submit on sixth digit; one visible Form. Secondary:
  resend button (`name="intent" value="resend"`, disabled until `resendAvailableAt`) and "Feil
  nummer? Endre" → Link to contact. Back: Link to contact.
- Action: `intent=verify` → `verifyAppointmentSessionUserMobile` → set auth cookies from the
  response tokens → `redirect(overview)`. `intent=resend` →
  `resendAppointmentSessionMobileChallenge`, which returns a **new**
  `PublicMobileChallengeResponseDto` (`challengeId`, `maskedMobile`, `expiresAt`,
  `resendAvailableAt`, `remainingAttempts`, `nextStep`) → `redirect` to self with the new
  `challengeId`; the reloaded screen takes its cooldown state from the payload fields. Wrong
  code → return error, stay.

### 3.6 overview

- Loader: `requireBookingReady` (session + requirements DONE) +
  `PublicAppointmentSessionController.getAppointmentSessionOverview`.
- Component: review sections; contact section "Endre" → Link to contact (renders RESUME). One
  visible Form; submit "Bekreft booking". Back: Link to contact — always contact, never
  verify-mobile (verify is a sub-step of contact, and its loader forwards when DONE anyway).
- Action: `PublicAppointmentSessionController.submitAppointmentSession` →
  `redirect(success?appointmentId=…)`.

### 3.7 success

- Loader: appointment by id. No booking-session dependency (session may be gone).
- Component: confirmation details; GUEST → completion card (frontend plan §3.4); returning →
  "Velkommen tilbake" flavor; FULL → nothing account-flavored. **No link back into
  contact/registration.**

## 4. Backend contract (verified against the generated SDK)

- `AppointmentSessionDto`: `sessionId`, `companyId`, `userId?`, `selectedProfileId?`,
  `selectedServices?`, `selectedStartTime?`, `steps?` — everything the §2 guard ladder needs
  exists today.
- `PublicSessionRequirementsDto`: `nextStep: 'CONTACT_FORM' | 'VERIFY_MOBILE' | 'DONE'` (note:
  the SDK enum value is `CONTACT_FORM`, not the planning name COLLECT_MOBILE — use the SDK
  names everywhere), plus `challengeId?`, `maskedMobile?`, `displayName?`,
  `canAttachAuthenticatedUser`, `authenticatedUserDisplayName?`, and resend/cooldown fields.
- `PublicIdentifyResponseDto`: `challengeId`, `maskedMobile`, `expiresAt`,
  `resendAvailableAt?`, `nextStep`.
- `PublicMobileChallengeResponseDto` (resend): new `challengeId`, `maskedMobile`, `expiresAt`,
  `resendAvailableAt?`, `remainingAttempts?`, `nextStep`.
- `PublicVerifyMobileResponseDto`: auth tokens + `nextStep`.

Nothing else is needed from backend for this renovation.

## 5. Email rule (restated for this plan)

Email appears exactly twice, both optional: the collapsed toggle on the contact form, and the
post-success completion card for GUEST users. There is no email verification, email OTP, email
next-step, or email blocking anywhere in the booking flow. If email-related states appear in
booking route code after this renovation, it is a defect.

## 7. Logging (flat, behavior-free)

One helper, two call sites per route, no wrappers around logic:

```ts
logBooking('select-time', 'action', { sessionId, call: 'submit-start-time', startTime, redirect: 'self' });
```

- Loader entry: routeId, method, path, sessionId, relevant session fields (profileId, service
  count, hasSelectedStartTime).
- Action exit: routeId, intent, backend call name, redirect target or error message.
- The `call` field names the SDK method invoked — flat route logs around direct SDK calls,
  no wrapper.
- Nothing else. A booking's story is then readable as ~12 flat lines. If route middleware is
  available in the router version, the loader-entry line may live there — but only logging,
  never decisions.

## Appendix A — Commit 1 reference implementation: select-time

The whole route in one file. One visible form. One action intent. Continue is a Link. No
hidden forms, no shared action bar, no client state for booking data. Note: `getBookingSession`,
`bookingRoutes`, and `logBooking` are the renovation-target helpers from §1 (introduced in
commits 2/7); until then, commit 1 may use the current `requireBookingSession()` and
`getBookingRouteMap()` with the same structure. Presentational markup
(week tabs, date cards, hour columns) is kept from the current file — it renders data and owns
no navigation, which is allowed. Only the structural code is shown in full; unchanged visual
JSX is marked.

```tsx
// booking.public.appointment.session.select-time.route.tsx

import { Form, Link, redirect, useNavigation, useRevalidator } from 'react-router';
import { useEffect, useMemo, useState } from 'react';
import { PublicAppointmentSessionController } from '~/api/generated/booking';
import { resolveErrorPayload } from '~/lib/api-error';
import { redirectWithError } from '~/lib/flash-message.server';
import { getBookingSession } from '~/routes/booking/public/_utils/booking-session.server';
import { bookingRoutes } from '~/routes/booking/public/_utils/booking.route-map';
import { logBooking } from '~/routes/booking/public/_utils/booking-log.server';
import type { Route } from './+types/booking.public.appointment.session.select-time.route';

const ROUTE_ID = 'select-time';
const SCHEDULE_REFRESH_MS = 30_000;

// ---------- loader: read session, validate prerequisites, fetch page data ----------

export async function loader({ request }: Route.LoaderArgs) {
  const session = await getBookingSession(request); // returns session or throws redirect

  if (!session.selectedProfileId) throw redirect(bookingRoutes.employee);
  if (!session.selectedServices?.length) throw redirect(bookingRoutes.selectServices);

  logBooking(ROUTE_ID, 'loader', {
    sessionId: session.sessionId,
    hasSelectedStartTime: Boolean(session.selectedStartTime),
  });

  const schedulesResponse = await PublicAppointmentSessionController.getAppointmentSessionSchedules({
    query: { sessionId: session.sessionId },
  });

  return {
    session,
    schedules: schedulesResponse.data?.data ?? [],
  };
}

// ---------- action: one intent — save the clicked slot, PRG back to self ----------

export async function action({ request }: Route.ActionArgs) {
  const session = await getBookingSession(request);
  const formData = await request.formData();
  const startTime = formData.get('startTime');

  if (typeof startTime !== 'string' || !startTime) {
    return redirectWithError(request, bookingRoutes.selectTime, 'Velg et tidspunkt');
  }

  try {
    await PublicAppointmentSessionController.submitAppointmentSessionStartTime({
      query: { sessionId: session.sessionId, selectedStartTime: startTime },
    });
    logBooking(ROUTE_ID, 'action', { sessionId: session.sessionId, startTime, redirect: 'self' });
    return redirect(bookingRoutes.selectTime); // PRG: reload shows backend-selected slot
  } catch (error) {
    const { message } = resolveErrorPayload(error, 'Kunne ikke lagre tidspunkt');
    logBooking(ROUTE_ID, 'action', { sessionId: session.sessionId, startTime, error: message });
    return redirectWithError(request, bookingRoutes.selectTime, message);
  }
}

// ---------- component: one visible form, Continue is a Link ----------

export default function SelectTimePage({ loaderData }: Route.ComponentProps) {
  const { session, schedules } = loaderData; // session guaranteed by loader — no null branch
  const navigation = useNavigation();
  const isSubmitting = navigation.state === 'submitting';

  // Backend is the source of truth for the SELECTION.
  const selectedStartTime = session.selectedStartTime ?? null;

  // View-only browsing state (which week/date the user is LOOKING at) — not booking data.
  const weekGroups = useMemo(() => groupSchedulesByWeek(schedules), [schedules]);
  const [weekIndex, setWeekIndex] = useState(() => initialWeekIndex(weekGroups, selectedStartTime));
  const [viewDate, setViewDate] = useState<string | null>(() =>
    selectedStartTime ? findScheduleWithTime(schedules, selectedStartTime) : null,
  );

  // Keep slots fresh: re-fetch loader data every 30s while idle and visible.
  const revalidator = useRevalidator();
  useEffect(() => {
    if (navigation.state !== 'idle' || revalidator.state !== 'idle') return;
    const id = window.setTimeout(() => {
      if (document.visibilityState === 'visible') revalidator.revalidate();
    }, SCHEDULE_REFRESH_MS);
    return () => window.clearTimeout(id);
  }, [navigation.state, revalidator]);

  return (
    <BookingStepLayout label="Velg tidspunkt" title="Hva er et tidspunkt du ønsker?">
      {/* THE form. Every slot button below submits it with its own value. */}
      <Form method="post">
        {/* Quick book — a submit button like any other slot */}
        {/* ...existing "Raskeste tiden" markup, button:
              <button type="submit" name="startTime" value={earliestSlot.time} ...> */}

        {/* Week navigator — pure view state (setWeekIndex), unchanged markup */}

        {/* Date cards — pure view state (setViewDate), unchanged markup */}

        {/* Time slots — each slot is a plain submit button in THIS form: */}
        {/*   <button type="submit" name="startTime" value={slot.startTime}
               disabled={isSubmitting}
               aria-pressed={slot.startTime === selectedStartTime}
               className={cn(slotClasses, slot.startTime === selectedStartTime && selectedClasses)}>
             {formatTime(slot.startTime)}
           </button> */}
      </Form>

      {/* Footer — owned by this route. Back is a Link. Continue is a Link, gated on session. */}
      <footer className="booking-footer">
        <Link to={bookingRoutes.selectServices} className="btn-secondary">
          Tilbake
        </Link>
        {selectedStartTime ? (
          <Link to={bookingRoutes.contact} className="btn-primary">
            Fortsett
          </Link>
        ) : (
          <button type="button" disabled className="btn-primary">
            Velg et tidspunkt
          </button>
        )}
      </footer>
    </BookingStepLayout>
  );
}

// ---------- pure helpers, this file only (groupSchedulesByWeek, getWeekNumber,
//            findScheduleWithTime, initialWeekIndex, formatTime imports, etc.) ----------
```

What a reviewer should verify in this file, in order:

1. There is exactly one `<Form>`, it is visible, and every submit button in it carries
   `name="startTime"` with a value. No `intent` field exists anywhere.
2. The action has one job. It cannot redirect to contact — only the Link can go there, and the
   Link only renders when the _backend session_ has a start time. If the Link ever renders
   wrongly, contact's loader bounces back (§2 guard ladder) — two independent checks, zero
   shared code.
3. `useState` holds only what the user is looking at (week, date). The selected time is read
   from `session` on every render; slot highlight and Continue-visibility derive from the same
   value and cannot disagree.
4. No `BookingBottomActionBar`, no `form=` attribute, no refs mirroring router state, no
   `console.info`. Two `logBooking` lines server-side tell the whole story.
5. Hooks run unconditionally at the top — the null-session branch is gone because the loader
   guarantees the session (it throws a redirect otherwise).

Behavior change to be aware of (deliberate): clicking a slot is a normal form navigation, so
the page does a PRG round-trip per selection instead of a background fetcher save. That is the
boring, no-JS-safe choice, and with loader data cached at the session it is fast. If real-world
latency makes slot-clicks feel sluggish on mobile, the smallest permitted upgrade is switching
that one form to `useFetcher` inside this same file — nothing else about the design changes.
