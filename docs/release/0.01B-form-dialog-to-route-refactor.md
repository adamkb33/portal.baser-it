# 0.01B Form Dialog To Route Refactor

## Objective

Replace route-local form dialogs with real routes and route-based forms.

This refactor is specifically about forms that currently open inside an overlay and submit within the same page context. Those flows should become proper pages so they are:

- addressable
- navigable
- bookmarkable
- easier to validate
- easier to recover from
- easier to keep consistent with the shared template system

## Important Scope Rule

This refactor applies to form dialogs only.

We are **not** replacing confirmation dialogs such as:

- delete confirmation
- cancel confirmation
- decline confirmation

Those can remain dialogs because they are short confirmation actions, not data-entry flows.

## Product Decision

The preferred pattern should be:

- collection page
- `create` page
- `edit` page

Recommended route shape:

- `/create` for new resources
- `/:id/edit` for existing resources

This is better than query-param mode switching for these flows because:

- the user is clearly in a new task
- it is easier to handle back navigation
- route loaders/actions become explicit
- validation and submit failure handling become cleaner

## 1. Company Admin Contacts

### Current Dialog

- [contact.form-dialog.tsx](/Users/adambaser/Documents/portal.pitell/app/routes/company/admin/contacts/_components/contact.form-dialog.tsx)

### Current Call Sites

- [company.admin.contacts.route.tsx](/Users/adambaser/Documents/portal.pitell/app/routes/company/admin/contacts/company.admin.contacts.route.tsx)
- [contact-selector.tsx](/Users/adambaser/Documents/portal.pitell/app/routes/company/booking/_components/contact-selector.tsx)

### Current Behavior

- create contact via modal
- edit contact via modal
- submits directly to API routes

### Required Route Refactor

Add route pages:

- `company.admin.contacts.create`
- `company.admin.contacts.edit`

Recommended path shape:

- `/company/admin/contacts/create`
- `/company/admin/contacts/:id/edit`

### Route Responsibilities

- `create`
  - render contact form page
  - submit via route `action`
  - redirect back to contacts list or `returnTo`
- `edit`
  - load existing contact by id
  - render same shared form page
  - submit via route `action`
  - redirect back to contacts list or `returnTo`

### Shared Component Strategy

Extract the form body into a reusable shared route component:

- `ContactFormPage` or `ContactFormSection`

The route should own:

- loader
- action
- page shell
- redirect behavior

### Special Note

Because contacts are also created from booking flows, these routes should support:

- optional `returnTo` query param

That allows booking appointment flows to leave the page, create a contact, then return safely.

## 6. Booking Flow Contact Creation

### Current Dialog

- [ContactFormDialog](/Users/adambaser/Documents/portal.pitell/app/routes/company/admin/contacts/_components/contact.form-dialog.tsx) is reused from [contact-selector.tsx](/Users/adambaser/Documents/portal.pitell/app/routes/company/booking/_components/contact-selector.tsx)

### Current Behavior

- user can create a contact without leaving the booking appointment create flow

### Required Route Refactor

Do **not** create another separate booking-only contact form if avoidable.

Recommended strategy:

- reuse `company.admin.contacts.create`
- pass `returnTo` back into the appointment-create flow

Example:

- `/company/admin/contacts/create?returnTo=/company/booking/appointments/create/existing-user?...`

### Why

- avoids duplicate forms
- keeps contacts as a single resource domain
- still allows route-based flow recovery

Suggested route structure:

- `app/routes/company/admin/contacts/create/...`
- `app/routes/company/admin/contacts/$id/edit/...`
- `app/routes/company/admin/employees/invite/...`
- `app/routes/company/admin/employees/$userId/edit/...`
- `app/routes/company/booking/admin/service-groups/create/...`
- `app/routes/company/booking/admin/service-groups/$id/edit/...`
- `app/routes/company/booking/admin/service-groups/services/create/...`
- `app/routes/company/booking/admin/service-groups/services/$id/edit/...`
- `app/routes/company/booking/profile/schedule-unavailability/create/...`
- `app/routes/company/booking/profile/schedule-unavailability/$id/edit/...`

If the project avoids `$param` naming and prefers file-name explicitness, mirror the existing route naming style accordingly. The important part is the URL model, not the exact file-name convention.

## Recommended Action Strategy

For these refactors, prefer:

- route `loader`
- route `action`
- shared form component
- redirect with flash/success feedback

Avoid:

- client-side submit directly to API route from dialog state
- keeping form state trapped in modal-only local state
- duplicating the same form in multiple route trees

## Refactor Priority

### Wave 1

- booking profile schedule unavailability
- booking admin services
- booking admin service groups

These are the worst modal fits because the forms are dense.

### Wave 2

- company admin contacts
- company admin employees invite/edit

These are operational CRUD flows and should also move, but the pain level is slightly lower than the booking-admin forms.

### Wave 3

- booking-flow contact creation via `returnTo`
- any remaining shared picker/dialog form cases

## Definition of Done

- form overlays are removed for these resource flows
- each flow has a create and/or edit page route
- route actions own backend submission
- redirects and feedback are explicit
- route map is updated
- no critical CRUD form depends on modal-only local state
